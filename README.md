# tg-notify

GitHub Action для уведомлений CI/CD в Telegram: **одно сообщение на весь запуск**, которое обновляется
на месте по мере выполнения шагов. Звук только при провале.

```
⏳ Сборка: выполняется                 ← жирный
• Репозиторий: qu1nqqy/rustos          ← значения моноширинные
• Ветка: master
• Автор: qu1nqqy

📝 test                                ← жирный
┃ ✅ actions/checkout@v7               ← шаги задачи в цитате
┃ ✅ cargo fmt --check
┃ ⏳ cargo clippy
┃ ⏳ Tests in QEMU

📝 release ⏳                          ← задача ещё не началась

[ Запуск ]  [ Коммит ]                 ← ссылки только в кнопках
```

- **Один вызов в начале задачи.** Статус остальных шагов action берёт из GitHub API сам: фоновый процесс
  опрашивает его раз в 5 с и правит сообщение, только если текст изменился.
- **Тихо, пока всё хорошо.** Сообщение и все его правки беззвучные. При провале приходит отдельный ответ
  **со звуком** с кнопкой «Открыть шаг». При успехе ничего нового не приходит.
- **Несколько задач — одно сообщение.** Следующая задача получает `message_id` через `needs` и дописывает свою секцию.
- **Темы.** Каждый проект пишет в свою тему группы.
- **Релизы.** `mode: release` отправляет новое сообщение о релизе с файлами и закрепляет его в теме.
- **Не ломает сборку.** Нет секретов, нет прав, Telegram недоступен — будет предупреждение в логе, задача пройдёт.

## Быстрый старт

1. Создайте бота и группу с темами, узнайте `chat_id` и `topic_id` — [Бот и группа](#бот-и-группа).
2. Задайте в репозитории секреты `TELEGRAM_TOKEN`, `TELEGRAM_CHAT_ID` и **переменную** `TELEGRAM_TOPIC_ID` —
   [Секреты](#секреты-две-схемы).
3. Добавьте шаг **первым** в задачу и дайте workflow право `actions: read`:

```yaml
# .github/workflows/build.yml
name: build
on: [push, pull_request]

permissions:
  contents: read
  actions: read          # обязательно: action читает статус шагов

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: qu1nqqy/tg-notify@v1      # первым шагом
        with:
          token: ${{ secrets.TELEGRAM_TOKEN }}
          chat_id: ${{ secrets.TELEGRAM_CHAT_ID }}
          topic_id: ${{ vars.TELEGRAM_TOPIC_ID }}
          # title: Проверка             # если pipeline ничего не собирает
      - uses: actions/checkout@v7
      - run: make test
```

## Бот и группа

1. Создайте бота у [@BotFather](https://t.me/BotFather) (`/newbot`) и сохраните токен.
2. Создайте группу и включите в ней **темы**: настройки группы → «Темы». Для каждого проекта создайте свою тему.
   Удобно завести одну группу на организацию или профиль и тему на каждый репозиторий.
3. Добавьте бота в группу.
   - Для статуса сборок достаточно, чтобы бот был участником.
   - Для режима `release` сделайте бота **администратором** с правом «Закреплять сообщения».
4. Узнайте `chat_id` и `topic_id`.

   **По ссылке.** Нажмите на любое сообщение **внутри темы** → «Копировать ссылку»:

   ```
   https://t.me/c/1234567890/42/100
                 └── chat ──┘ └┘ └─ id сообщения
                          topic
   ```

   `chat_id` = `-100` + первое число = `-1001234567890`, `topic_id` = `42`.
   Если в ссылке только **два** числа (`t.me/c/1234567890/100`), сообщение из темы «General»: второе число —
   это id сообщения, а не темы. В «General» пишите без `topic_id`.

   **Через Bot API** (надёжнее). Отправьте в нужную тему `/start@имя_бота`. Команды бот видит даже в режиме
   приватности. Затем выполните:

   ```sh
   read -s T; curl -s "https://api.telegram.org/bot$T/getUpdates" | grep -o '"message_thread_id":[0-9]*\|"id":-100[0-9]*' | tail -2
   ```

   Получите `"id":-100…` (это `chat_id`) и `"message_thread_id":…` (это `topic_id`).

   Проверить, что бот видит чат: `curl -s "https://api.telegram.org/bot$T/getChat?chat_id=-1001234567890"`
   должен вернуть `"ok":true`.

## Секреты: две схемы

Action сам секреты не читает, их передаёт workflow через `${{ secrets.X }}`. GitHub ищет секрет по порядку:
**окружение → репозиторий → организация**. Поэтому workflow один и тот же для организации и для профиля.
Различается только место, где заданы значения.

| имя | тип | где задавать |
|-----|-----|--------------|
| `TELEGRAM_TOKEN` | секрет | организация или репозиторий |
| `TELEGRAM_CHAT_ID` | секрет | организация или репозиторий |
| `TELEGRAM_TOPIC_ID` | **переменная** (`vars.`) | обычно репозиторий: у каждого проекта своя тема |

`TELEGRAM_TOPIC_ID` не секрет, а переменная. Если завести его секретом, GitHub будет заменять это число на
`***` **во всех логах**. Например, при теме `4` строка `400 Bad Request` превратится в `***00 Bad Request`,
а время `07:20:34` — в `07:20:3***`.

### Схема «организация»

Одна группа на организацию, по теме на проект.

1. Settings организации → Secrets and variables → Actions → **New organization secret**:
   `TELEGRAM_TOKEN`, `TELEGRAM_CHAT_ID`. В «Repository access» выберите нужные репозитории.
2. В каждом репозитории: Settings → Secrets and variables → Actions → вкладка **Variables** →
   `TELEGRAM_TOPIC_ID`.
3. Workflow — как в «Быстром старте».

Секрет репозитория с тем же именем **переопределяет** секрет организации. Так можно направить один
репозиторий в другую группу. Если секреты организации должны иметь приоритет, задайте их под другим именем:

```yaml
token: ${{ secrets.ORG_TELEGRAM_TOKEN || secrets.TELEGRAM_TOKEN }}
chat_id: ${{ secrets.ORG_TELEGRAM_CHAT_ID || secrets.TELEGRAM_CHAT_ID }}
```

> **Тариф GitHub Free.** Секреты и переменные **уровня организации недоступны приватным репозиториям**
> на бесплатном тарифе организации ([документация](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)).
> В workflow приватного репозитория `secrets.TELEGRAM_TOKEN` будет пустым, и action только выведет
> предупреждение. Для приватных репозиториев на Free задайте секреты в самом репозитории (как в схеме
> «профиль») или перейдите на тариф Team. Публичным репозиториям секреты организации доступны и на Free.

### Схема «профиль»

У личного аккаунта нет секретов уровня профиля, поэтому в каждом репозитории свои значения. Токен и группа
могут быть одни на все репозитории, тема у каждого своя. Workflow — тот же.

```sh
gh secret set TELEGRAM_TOKEN -R owner/repo                     # спросит значение, в историю shell не попадёт
gh secret set TELEGRAM_CHAT_ID -R owner/repo --body -1001234567890
gh variable set TELEGRAM_TOPIC_ID -R owner/repo --body 42
```

## Пример: две задачи и релиз

`test` создаёт сообщение и отдаёт `message_id` наружу. `release` (только push в `master`) дописывает в то же
сообщение свою секцию, создаёт релиз на GitHub и отправляет о нём отдельное закреплённое сообщение с файлами.

```yaml
name: build
on:
  push:
  pull_request:

permissions:
  contents: read
  actions: read

jobs:
  test:
    runs-on: ubuntu-latest
    outputs:
      tg_message_id: ${{ steps.tg.outputs.message_id }}
    steps:
      - id: tg
        uses: qu1nqqy/tg-notify@v1
        with:
          token: ${{ secrets.TELEGRAM_TOKEN }}
          chat_id: ${{ secrets.TELEGRAM_CHAT_ID }}
          topic_id: ${{ vars.TELEGRAM_TOPIC_ID }}
      - uses: actions/checkout@v7
      - run: cargo fmt --check
      - run: cargo clippy -- -D warnings
      - run: cargo test

  release:
    needs: test
    if: github.event_name == 'push' && github.ref == 'refs/heads/master'
    runs-on: ubuntu-latest
    permissions:
      contents: write   # gh release create
      actions: read     # свой блок permissions заменяет общий целиком — повторяем actions: read
    steps:
      - uses: qu1nqqy/tg-notify@v1
        with:
          token: ${{ secrets.TELEGRAM_TOKEN }}
          chat_id: ${{ secrets.TELEGRAM_CHAT_ID }}
          topic_id: ${{ vars.TELEGRAM_TOPIC_ID }}
          message_id: ${{ needs.test.outputs.tg_message_id }}
      - uses: actions/checkout@v7
      - run: make images
      - run: gh release create "v0.1.${{ github.run_number }}" dist/*.bin --generate-notes
        env:
          GH_TOKEN: ${{ github.token }}
      - uses: qu1nqqy/tg-notify@v1
        with:
          mode: release
          token: ${{ secrets.TELEGRAM_TOKEN }}
          chat_id: ${{ secrets.TELEGRAM_CHAT_ID }}
          topic_id: ${{ vars.TELEGRAM_TOPIC_ID }}
          files: dist/*.bin
```

Если `message_id` пустой (например, у первой задачи не было секретов), задача просто отправит новое сообщение.

## Входы и выходы

| вход | по умолчанию | описание |
|------|--------------|----------|
| `token` | — | токен бота. Пустой — предупреждение, уведомление пропускается |
| `chat_id` | — | id группы (`-100…`). Пустой — как с `token` |
| `topic_id` | — | id темы (`message_thread_id`). Пустой — сообщение в «General» или в обычный чат |
| `message_id` | — | продолжить сообщение предыдущей задачи (`needs.<job>.outputs.…`) |
| `mode` | `pipeline` | `pipeline` — статус шагов; `release` — сообщение о релизе |
| `title` | `Сборка` | заголовок: `✅ <title>: успешно`. Например `Проверка`, `Деплой`. `{workflow}` заменяется именем workflow |
| `files` | — | `release`: glob файлов, можно несколько строк; каждый до 50 МБ |
| `tag` | авто | `release`: тег релиза. По умолчанию тег из `ref` или релиз, опубликованный этим запуском |
| `notes` | авто | `release`: заметки. По умолчанию описание релиза на GitHub, сокращённое |
| `poll_interval` | `5` | период опроса GitHub API, секунд (не меньше 3) |
| `github_token` | `${{ github.token }}` | чтение шагов (`actions: read`) и релизов (`contents: read`) |

| выход | описание |
|-------|----------|
| `message_id` | id сообщения. В `pipeline` его передают следующей задаче. В `release` это id сообщения о релизе |

## Что и как показывается

**Шапка.** Заголовок жирным и три строки: репозиторий, ветка, авторы.

- Заголовок: `⏳ Сборка: выполняется` → `✅ Сборка: успешно` / `❌ Сборка: ошибка` / `❌ Сборка: отменено`.
  Слово «Сборка» задаётся входом `title`. Форма «X: состояние» подходит к любому слову без согласования по роду.
- Ветка: при pull_request — исходная ветка PR, иначе ветка или тег из `ref`.
- Автор: при push — уникальные авторы коммитов из `github.event.commits`, при pull_request — автор PR,
  в остальных случаях (`workflow_dispatch`, `schedule`, …) — `github.actor`.

**Задачи.** Секция `📝 имя` на каждую задачу запуска, шаги в цитате.

- Значки: ⏳ ждёт или выполняется, ✅ успех, ❌ провал или отмена. Пропущенные шаги скрыты.
- Скрыты служебные шаги: «Set up job», «Complete job», `Post …` и сам tg-notify (даже если у шага своё имя).
- У имён шагов убирается префикс `Run `, который GitHub ставит по умолчанию: `Run npm test` → `npm test`.
- Завершённая успешная задача с длинным списком шагов показывается в **сворачиваемой** цитате,
  остальное раскрывается нажатием.
- Задача, которая есть в API, но ещё не началась: `📝 release ⏳`.
- Пропущенная задача (`if` не выполнился) не показывается. Первая задача не знает заранее, будет ли вторая,
  поэтому секция задачи появляется, только когда задача появилась в API.

**Итог** (жирным, в конце):

```
✅ Готово за 4:12        ❌ Упало: cargo clippy        ❌ Отменено
```

**При провале** в ответ на основное сообщение приходит отдельное сообщение **со звуком**:

```
❌ qu1nqqy/rustos: упало на cargo clippy
[ Открыть шаг ]                        ← ведёт прямо на упавший шаг в логе GitHub
```

При отмене такой ответ не отправляется: отмену запускает человек, он и так знает.

**Кнопки** под сообщением зависят от события: «Запуск» и «Коммит» всегда, «PR» — для pull_request,
«Релиз» — если запуск опубликовал релиз. В тексте ссылок нет, предпросмотр выключен.

**Длинные запуски.** Лимит Telegram — 4096 символов. Если текст не помещается, он сокращается по шагам:
1. успешные задачи сворачиваются в одну строку `📝 build ✅ (шагов: 40)`;
2. скрываются успешные шаги, вместо них счётчик;
3. обрезаются длинные имена;
4. в крайнем случае текст обрезается по строкам.

Итоговая строка сохраняется всегда. Логи в сообщение не попадают: их удобнее смотреть на GitHub по кнопке.

## Режим release

`mode: release` отправляет в тему **новое** сообщение, отдельно от сообщения о pipeline:

```
🚀 Релиз v0.1.42
• Репозиторий: qu1nqqy/rustos

┃ ## Что нового        ← заметки в сворачиваемой цитате
┃ - …

[ Релиз ]  [ Коммит ]
```

- **Какой релиз:** с тегом из входа `tag`. Если `tag` пустой — тег из `ref` (запуск по тегу). Если и его нет —
  самый новый релиз, **опубликованный после начала запуска**. Поэтому шаг ставится после `gh release create`.
  Если релиз не найден, сообщение всё равно уйдёт, но без кнопки «Релиз», а вместо тега будет короткий sha.
- **Заметки:** вход `notes` или описание релиза на GitHub, сокращённое под лимит.
- **Файлы** из `files` (glob, можно несколько строк):
  - один файл — документом, текст в подписи, кнопки под ним;
  - несколько — текстовое сообщение с кнопками, а в ответ на него альбомы документов по 10;
  - файл больше 50 МБ (лимит Bot API) не отправляется, в тексте будет «Больше 50 МБ, скачать в релизе».
- **Закреп:** бот закрепляет сообщение (в группе с темами у каждой темы свои закрепы). Нужны права
  администратора с правом закреплять; без них будет предупреждение.
- Сообщение о релизе беззвучное, как и всё, кроме ответа о провале.

## Как это работает

- **main** — шаг tg-notify. Получает список задач запуска, находит свою задачу (по имени раннера) и свой шаг.
  Отправляет беззвучное сообщение или правит переданное по `message_id`. Затем запускает отдельный фоновый
  процесс и сразу завершается: следующие шаги не ждут.
- **Фоновый процесс** раз в `poll_interval` секунд запрашивает
  `GET /repos/{owner}/{repo}/actions/runs/{run_id}/attempts/{attempt}/jobs` и правит сообщение, только если
  текст изменился. Учитывается только текущая попытка (`re-run` — новое состояние).
- **post** выполняется в конце задачи всегда (`post-if: always()`), в том числе при провале и отмене.
  Он останавливает фоновый процесс и ждёт, пока GitHub допишет статус последних шагов. Затем выставляет итог,
  а если упала **эта** задача — отправляет ответ со звуком. Лог фонового процесса выводится здесь же
  в свёрнутой группе «tg-notify: лог фонового процесса».

Ограничения Telegram учтены: при обычном опросе получается не больше одной правки в 5 с, а на ответ `429`
action ждёт `retry_after`. Токен бота маскируется в логах.

**Ограничения:**

- Сообщение «закрывает» задача, которая завершается последней. Когда `test` закончилась, а `release` ещё
  не стартовала, шапка на время станет «✅ Сборка: успешно». Задача `release` вернёт её в «⏳» и допишет свою секцию.
- Задача без шага tg-notify видна в сообщении, но итог за неё некому выставить. Добавляйте шаг в каждую задачу.
- Параллельным задачам `message_id` недоступен: каждая с шагом tg-notify отправит своё сообщение.
  Одно сообщение получается у задач, связанных через `needs`.
- Нужен раннер с поддержкой `node24` (GitHub-hosted подходят; self-hosted — актуальной версии).

## Если не работает

Все ошибки action пишет предупреждением (`##[warning]tg-notify: …`) в логе своего шага или его post-шага.

| сообщение | причина и что делать |
|-----------|----------------------|
| `пустой token и chat_id — уведомление пропущено` | секреты не заданы или не доступны этому репозиторию. Приватный репозиторий в организации на Free секреты организации не видит — см. [Секреты](#секреты-две-схемы) |
| `400 Bad Request: chat not found` | неверный `chat_id` (нужен вид `-100…`) или бота нет в группе. Проверка: `getChat`, см. [Бот и группа](#бот-и-группа) |
| `400 Bad Request: message thread not found` | неверный `topic_id`: часто это id сообщения из «General», а не темы. Узнайте через `getUpdates` |
| `401 Unauthorized` | неверный токен бота |
| `403 Forbidden: bot is not a member` / `bot was kicked` | добавьте бота в группу |
| `не удалось получить шаги задачи … actions: read` | в `permissions` нет `actions: read`. Если у задачи свой блок `permissions`, укажите там |
| `не удалось закрепить сообщение` | боту нужны права администратора с правом закреплять |
| `релиз этого запуска не найден` | шаг `mode: release` стоит до создания релиза, релиз — черновик, или нужно передать `tag` |
| в логе `***` вместо цифр | `TELEGRAM_TOPIC_ID` задан секретом, а не переменной |

## Разработка и версии

```sh
npm ci
npm test           # vitest: текст, фильтры, экранирование, обрезка, кнопки, авторы, релиз, Telegram API
npm run typecheck
npm run build      # ncc → dist/index.js (dist коммитится: GitHub запускает его как есть)
npm run all        # всё сразу
```

- Исходники в `src/`: `render.ts` — чистые функции построения текста, `pipeline.ts` — main, фоновый
  процесс и post, `release.ts` — режим release, `telegram.ts` и `github.ts` — клиенты API.
- CI собирает `dist` и падает, если он не совпадает с закоммиченным. Задача `smoke` вызывает action на
  самом себе (`uses: ./`) и шлёт сообщение, если в репозитории заданы секреты.
- `TELEGRAM_API_URL` в окружении задаёт свой адрес Bot API: локальный сервер или заглушку для тестов.

Версии: точные теги `v1.0.0`, `v1.1.0`, … и плавающий `v1`, который переносится на последний `v1.x.y`.
Подключайте `@v1`, чтобы получать исправления, или точный тег, чтобы версия не менялась.

```sh
npm run all && git commit -am "fix: …"
git tag -a v1.1.1 -m v1.1.1 && git tag -f v1
git push origin main v1.1.1 && git push -f origin v1
```
